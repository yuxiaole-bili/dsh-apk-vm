# scrcpy 5.0.1 wire protocol — headless relay notes

Byte-level protocol reference for the **APK VM preview** plugin. It documents exactly what the
open-source `scrcpy-server` v5.0.1 speaks on the wire, so a dependency-free Node relay
(`lib/scrcpy.js`) can consume the H.264 stream and inject input **without** the scrcpy desktop
client (no SDL, no FFmpeg, no GUI).

- Upstream: [Genymobile/scrcpy](https://github.com/Genymobile/scrcpy), **Apache-2.0**, release tag `v5.0.1`
  (published 2026-10-08).
- Server artifact used by this plugin: `vendor/scrcpy-server-v5.0.1.jar`
  (sha256 `764eb6f79811d5211fe9df341120882ba9994c7a61b897d7bf3fb662e53bc536`, 733 930 bytes —
  identical to the digest reported by the GitHub release-assets API for asset `scrcpy-server-v5.0.1`).
- Sources: the full v5.0.1 tree is vendored under `src/scrcpy-5.0.1/` (`app/` = desktop client,
  `server/` = Android server). Everything below was read from that tree, not guessed.
- Version compatibility: the protocol is explicitly **internal and unstable across versions**;
  client and server versions must match exactly (see `doc/develop.md` § Protocol). This relay hard-codes
  `5.0.1` and fails cleanly on mismatch.

Legend: all integers are **big-endian** unless a table says otherwise. `uN`/`iN` = unsigned/signed
N-bit integer. `u16fp` = unsigned 16-bit fixed point, `i16fp` = signed 16-bit fixed point (§5.4).

---

## 1. Roles and transport

Two processes:

| role | where | what |
| --- | --- | --- |
| `scrcpy-server.jar` | Android device, launched by `app_process` as user `shell` | captures the screen with `MediaCodec`, sends H.264 packets on the *video* socket, reads control messages on the *control* socket |
| our relay (`lib/scrcpy.js`) | Windows host, Node ESM | pushes/starts the server, connects the sockets, parses H.264 access units + codec metadata, encodes touch/key/scroll/text control messages |

Sockets are up to three: **video**, **audio**, **control**, opened in that order. In our relay audio is
always disabled (`audio=false`), so there are exactly **two** sockets: video first, control second.

At the network level the roles can be inverted with an adb tunnel:

- **forward** (our default, matches the task spec): `adb forward tcp:<port> localabstract:scrcpy_<scid>`.
  The device listens on an abstract Unix socket, the host relay connects twice.
- **reverse** (scrcpy client default, not usable over `adb connect` devices): relay listens on
  `127.0.0.1:<port>`, `adb reverse localabstract:scrcpy_<scid> tcp:<port>`, the device connects twice.

`<scid>` is a random **31-bit non-negative** identifier generated by the client and passed to the
server as `scid=%08x`; the abstract socket name is `scrcpy_` + 8 lowercase hex digits
(`app/src/scrcpy.c:295`, `app/src/server.c:24,1074`). The server also accepts `scid=-1`, in which
case the abstract name is the plain string `scrcpy` (only useful for standalone servers).

## 2. Launching the server

### 2.1 Commands

Exact sequence used by scrcpy v5.0.1 (`app/src/server.c:208-253`, `app/src/adb/adb.c:249-285`,
`doc/develop.md` § Execution):

```text
adb push scrcpy-server-v5.0.1.jar /data/local/tmp/scrcpy-server.jar

# forward mode (our default):
adb forward tcp:27183 localabstract:scrcpy_<scid>

# then, for the lifetime of the session:
adb -s <serial> shell CLASSPATH=/data/local/tmp/scrcpy-server.jar \
    app_process / com.genymobile.scrcpy.Server 5.0.1 \
    scid=<scid-hex> log_level=info audio=false tunnel_forward=true \
    max_size=720 video_bit_rate=4000000
```

Notes:

- The first argument after the main class is the **client version string**; the server compares it to
  its own `BuildConfig.VERSION_NAME` and throws `IllegalArgumentException` unless they are identical
  (`server/.../Options.java:322-331`). The vendored JAR really is 5.0.1: the string `5.0.1` is present
  in its `classes.dex` at byte offset 1660771.
- `CLASSPATH=...` is passed as a *single* argv element before `app_process` (the `shell` command joins
  argv with spaces, so this must not contain spaces). `/` is a dummy arg required by `app_process`.
- All server logs are printed on **stdout** of the server process (`app/src/server.c:478` comment).
  The relay captures a bounded tail for diagnostics.
- Every `key=value` option after the version is optional; unknown keys are only warned about
  (`Options.java:571-573`). Options may be in any order.
- The forward rule is removed by the client after the two sockets are connected
  (`app/src/server.c:716-718`); existing TCP connections survive `adb forward --remove`.
  The relay does the same and removes it again in `stop()`.

## 3. Connection handshake

### 3.1 Socket order

With video enabled, audio disabled, control enabled:
`video` connection first, then `control` connection, accepted in that order by the server
(`server/.../device/DesktopConnection.java:56-116`). If audio were enabled it would be accepted
between them.

### 3.2 First socket — dummy byte (forward mode only)

In **forward** mode the server writes a single byte `0x00` on the *first* accepted socket
(when `send_dummy_byte` is true, the default), and only there
(`DesktopConnection.java:64-89`; `doc/develop.md` § Connection):

```
offset 0: u8 = 0x00   # dummy byte, only on first socket, only when tunnel_forward=true
```

Why: `adb forward` accepts a TCP connection even when nothing is listening on the device side, so a
client cannot tell a live server from a dead tunnel by `connect()` alone. scrcpy's client therefore
connects and does a blocking `read(1)`; if that returns 0 bytes it retries (100 attempts, 100 ms
apart — `app/src/server.c:489-539`). The relay uses the same "connect + read 1 byte, retry" probe.

In **reverse** mode no dummy byte is sent (`tunnelForward` branch only).

### 3.3 Device metadata

Immediately after the socket set-up, if `send_device_meta` (default true), the server writes the
device name on the *first* socket (video socket for us) — `DesktopConnection.java:155-165`:

```
offset 0..63: 64 bytes, UTF-8 device name, zero padded, truncated to 63 bytes at a UTF-8 boundary
```

Example device name: `Android SDK built for x86_64`. It is only used as a window title upstream; the
relay exposes it as `session.deviceName`.

Ordering for our (video+control) forward session:

```
relay connects video socket ──► server accepts video, writes dummy 0x00
relay reads 1 byte (dummy)   ──► success = server is really listening
relay connects control socket──► server accepts control
relay reads 64 bytes          ──► device name on the video socket
video socket now carries: codec id (u32) + session header (12 B) + frames
```

### 3.4 No socket-level framing beyond the above

There is no length-prefixed framing/version exchange on the sockets. The stream simply starts with
the bytes listed in §4 (video) and a stream of control messages (control, §5). Control messages from
the device to the client also flow on the control socket (§6).

## 4. Video stream (video socket)

`server/.../device/Streamer.java`, `app/src/demuxer.c`, `doc/develop.md` § Video and audio.

### 4.1 Stream metadata prelude (once per connection, when `send_stream_meta`)

When the stream starts (and after each encoder restart) the server writes:

```
u32 codec_id                    # 4 bytes, see table
u8  session_header[12]          # first session packet, see 4.2
```

Codec IDs (`server/.../video/VideoCodec.java`, ids are 4-byte ASCII):

| codec | id (hex) | ASCII | supported by our relay |
| --- | --- | --- | --- |
| H.264/AVC | `0x68323634` | `"h264"` | yes (only codec implemented) |
| H.265/HEVC | `0x68323635` | `"h265"` | detected, reported as unsupported |
| AV1 | `0x00617631` | `"av1"` | detected, unsupported |
| VP8 | `0x00767038` | `"vp8"` | detected, unsupported |
| VP9 | `0x00767039` | `"vp9"` | detected, unsupported |

Special codec-id values are control codes, not codecs (`Streamer.java:57-66`,
`app/src/demuxer.c:200-212`):

| value | meaning |
| --- | --- |
| `0x00000000` | stream explicitly disabled by the device (e.g. audio capture failure); video-only clients may continue |
| `0x00000001` | configuration error on the device; client must stop |

Audio codec ids (unused, listed for completeness): `"opus"` `0x6f707573`, `"aac"` `0x00616163`,
`"flac"` `0x666c6163`, `"raw"` `0x00726177`.

### 4.2 Session packet — 12 bytes

Sent for every capture session; a new session starts on rotation, resize, encoder restart, client
resize request. Distinguish it from a media-packet header by the MSB of byte 0
(`app/src/demuxer.c:122-133`, `Streamer.java:91-105`):

| offset | size | field | meaning |
| --- | --- | --- | --- |
| 0 | u8 | flags hi | `0x80` — session packet flag (bit 63 of the u64 view) |
| 1 | u8 | | 0 |
| 2 | u8 | | 0 |
| 3 | u8 | flags lo | bit 0 (`R`) = *client resized* (flex-display resize request, #6772); other bits 0 |
| 4 | u32 | width | video width in pixels of this session |
| 8 | u32 | height | video height in pixels of this session |

If read as two values: `u32 flags = 0x80000000 | clientResized`, then `u32 width`, `u32 height`.
Independently of the session flag, every new session is also accompanied by new SPS/PPS in a config
packet before the first frame (see 4.4).

### 4.3 Frame (media/config) packets — 12-byte header + payload

Sent for every encoded output buffer (`Streamer.java:107-124`, `app/src/demuxer.c:136-183`).

```
offset 0 .......... 7:  u64 pts_and_flags
offset 8 .......... 11: u32 packet_size          # payload bytes following this header
offset 12 ............. : payload[packet_size]   # raw MediaCodec output for this packet
```

`pts_and_flags` bits:

| bit | mask | field | meaning |
| --- | --- | --- | --- |
| 63 | `0x8000000000000000` | media-packet flag | always **0** for frame packets (MSB=1 identifies session packets instead) |
| 62 | `0x4000000000000000` | config packet | payload is codec configuration (H.264: SPS/PPS in Annex-B), not a picture |
| 61 | `0x2000000000000000` | key frame | IDR / sync frame |
| 0..60 | `0x1FFFFFFFFFFFFFFF` | PTS | presentation timestamp in **microseconds**, from `MediaCodec.BufferInfo.presentationTimeUs` |

Rules (`Streamer.java:107-124`):

- config packet: `pts_and_flags = 0x4000000000000000` exactly (PTS field 0, key-frame bit clear);
- picture packet: `pts_and_flags = pts [| 0x2000000000000000]` (key frame sets bit 61);
- `packet_size` must be > 0 (client treats 0 as a protocol error, `demuxer.c:141-144`);
- PTS is device-side monotonic microseconds. It is not wall-clock, but it is usable for ordering,
  frame pacing and (together with a start-of-stream anchor) for latency metrics.

Frame packets carry **Annex-B** byte streams for H.264 (`MediaCodec` output): NAL units prefixed with
`00 00 01` or `00 00 00 01` start codes. One packet normally equals one access unit (one encoded
picture, possibly containing SEI + IDR/slices). The relay parses out NAL units and keeps the whole
access unit together.

### 4.4 Codec configuration packet (H.264)

The first outputs of a `MediaCodec` encoder include a buffer flagged `BUFFER_FLAG_CODEC_CONFIG`
(`server/.../video/SurfaceEncoder.java:252-278`). The server forwards it as a config packet. For
H.264 it contains the codec-specific data (`csd-0`/`csd-1` merged), i.e. Annex-B
**SPS (NAL type 7)** and **PPS (NAL type 8)**. The desktop client treats the config packet as codec
extradata (`packet->pts = AV_NOPTS_VALUE`, `demuxer.c:171-175`) and, for H.264/H.265 only, **merges
it with the next media packet** before decoding (`demuxer.c:277-288,316-323`).

The relay deliberately does not merge. Instead it:

1. emits the config packet with `isConfig: true` so the browser can ignore it for decoding;
2. extracts SPS and PPS, builds the `AVCDecoderConfigurationRecord` (`avcC`) once via
   `buildAvcC(sps, pps)` and a WebCodecs codec string via `describeCodec(sps)`
   (`"avc1.PPCCLL"`);
3. caches them (`session.getVideoConfig()`), so a consumer that attaches late can still configure
   WebCodecs — the server only sends SPS/PPS once per encoder session, key frames repeat much more
   often (default I-frame interval in the server is finite, so a decoder must not rely on catching
   the very first config packet);
4. exposes `annexbToAvcc(buffer)` to convert Annex-B access units to length-prefixed samples when
   WebCodecs is configured **with** an `avcC` description.

Example capture of the first bytes after the handshake (audio disabled, defaults, illustrative):

```
0000  68 32 36 34                    codec id "h264"
0004  80 00 00 00                    session flags: session|no client-resize
0008  00 00 05 A0                    width  = 1440
000C  00 00 0A 00                    height = 2560
0010  40 00 00 00 00 00 00 1A        frame header: config flag, size 0x1A
0018  00 00 00 01 67 ...             payload: Annex-B SPS (+ PPS)
...
00xx  00 00 00 00 00 00 00 0F        frame header: PTS 0x0F µs? (first frame PTS small)
00xx  00 00 00 00 00 00 00 0F 5A     size
00xx  00 00 00 01 65 ...             IDR slice (keyframe bit 61 set in header)
```

(Widths/heights/sizes are illustrative; the real values come from the device.)

## 5. Control messages (client → device, control socket)

Serialization source of truth: `app/src/control_msg.c:103-211` (client) and
`server/.../control/ControlMessageReader.java` (server). The stream is **not length-framed**: each
message starts with a 1-byte type, and the type determines the fixed size (or the u8/u16/u32 length
field that follows). Unknown type = protocol error on the server side (`ControlMessageReader.read`
throws), so the relay may only send types listed below with well-formed payloads. Maximum control
message size 256 KiB (`1 << 18`).

### 5.2 `INJECT_TOUCH_EVENT` (type 2) — 32 bytes, the v5 touch message

| offset | size | field | notes |
| --- | --- | --- | --- |
| 0 | u8 | type | `2` |
| 1 | u8 | action | `MotionEvent.ACTION_*` low byte (see 5.5) |
| 2 | u64 | pointerId | see 5.5; generic finger = `0xFFFFFFFFFFFFFFFE` |
| 10 | i32 | x | in **video-frame** pixels (coordinate space of the current session w×h) |
| 14 | i32 | y | same space |
| 18 | u16 | screenWidth | width of the coordinate space (current session width) |
| 20 | u16 | screenHeight | current session height |
| 22 | u16 | pressure | u16fp 0…1 (`0xFFFF` = 1.0) |
| 24 | u32 | actionButton | `MotionEvent.BUTTON_*` of the button that triggered this event (0 for touch) |
| 28 | u32 | buttons | bitmask of buttons currently pressed (0 for touch) |

Server behaviour (`server/.../control/Controller.java:512-621`):

- `pointerId == 0xFFFFFFFFFFFFFFFF` (-1) means *mouse*: it may send `ACTION_HOVER_MOVE`, and
  non-primary buttons make it a real mouse event, otherwise it is treated as a finger.
- `pointerId` -2 (generic finger) / -3 (virtual finger) / any other value are touchscreen fingers;
  for touchscreen sources the server forces `buttons = 0` and sets tool type finger.
- `screenWidth`/`screenHeight` are used by the server's `PositionMapper` to map from *video frame*
  coordinates to device display coordinates. A browser must therefore send **video pixel**
  coordinates with the current decoded frame size, not `adb wm size` device pixels, whenever the
  stream is downscaled (`max_size=720` ⇒ yes, downscaled).
- Pointer IDs are tracked in a small pointer state (max 10); for a simple tap use
  `DOWN (pointerId=-2, pressure=1.0)`, `UP (same pointerId, pressure=0.0)`; add `MOVE` events between
  for swipes/drags.

### 5.3 `INJECT_SCROLL_EVENT` (type 3) — 21 bytes

| offset | size | field | notes |
| --- | --- | --- | --- |
| 0 | u8 | type | `3` |
| 1 | i32 | x | video-frame pixels |
| 5 | i32 | y | video-frame pixels |
| 9 | u16 | screenWidth | current session width |
| 11 | u16 | screenHeight | current session height |
| 13 | i16 | hScroll | i16fp of `hscroll/16`, clamped to [-1,1] |
| 15 | i16 | vScroll | i16fp of `vscroll/16`, clamped to [-1,1] |
| 17 | u32 | buttons | mouse buttons bitmask (0 typical for wheel) |

Scroll values are floats accepted in the range **[-16, 16]** (one "wheel notch" ≈ 1); the client
normalizes by `/16`, clamps and encodes as i16fp (`control_msg.c:128-141`), the server converts back
(`ControlMessageReader.java:121-128`, `Binary.java:34-37`). The scroll message is injected as
`ACTION_SCROLL` from a `SOURCE_MOUSE` device, so it works for wheel scrolling lists.

### 5.4 Fixed-point formats

`app/src/util/binary.h:66-93` (encode), `server/.../util/Binary.java` (decode):

- u16fp: `value = trunc(f * 65536)` for `0 ≤ f ≤ 1`; `f == 1.0` saturates to `0xFFFF`; decode
  `f = value == 0xFFFF ? 1.0 : value / 65536`.
- i16fp: `value = trunc(f * 32768)` for `-1 ≤ f ≤ 1`; `f == 1.0` saturates to `0x7FFF`; decode
  `f = value == 0x7FFF ? 1.0 : value / 32768`.

`CANCEL = 3`, `OUTSIDE = 4`, `POINTER_DOWN = 5`, `POINTER_UP = 6`, `HOVER_MOVE = 7`, `SCROLL = 8`,

### 5.6 Text injection limits

`INJECT_TEXT` carries at most **300 UTF-8 bytes** per message (`ControlMessageReader.java:17`,
`control_msg.c:113-117`). The relay splits longer strings on UTF-8 character boundaries. The desktop
client builds text from clipboard; the server replays it char by char with a
`KeyCharacterMap` (`Controller.java:451-480`), so it behaves like a virtual keyboard: characters that
the virtual keyboard cannot produce are dropped server-side (logged as warning). No NUL terminator is
written.

`SET_CLIPBOARD` text limit is `256 KiB - 14` bytes (`ControlMessageReader.java:16`).

## 6. Device messages (device → client, control socket)

The control socket is bidirectional. With `clipboard_autosync=false` the server only sends messages
in response to client requests. Format (`app/src/device_msg.h`, `app/src/device_msg.c`,
`server/.../control/DeviceMessageWriter.java`), again type byte first, BE integers:

| type | name | payload after type | total |
| --- | --- | --- | --- |
| 0 | `CLIPBOARD` | length u32 + UTF-8 text | 5 + n |
| 1 | `ACK_CLIPBOARD` | sequence u64 | 9 |
| 2 | `UHID_OUTPUT` | id u16, size u16, data | 5 + n |

Maximum 256 KiB. Unknown type is a fatal protocol error for the client
(`app/src/device_msg.c:74-77`). The relay parses valid messages (exposed through
`session.onDeviceMessage(fn)`) and, to stay bounded, treats an unknown type as a session error.

## 7. From the wire to WebCodecs (browser side)

The server encodes with Android `MediaCodec` (`server/.../video/SurfaceEncoder.java`). Output is
Annex-B H.264 access units plus one Annex-B SPS/PPS config packet per encoder session. The browser
half should configure `VideoDecoder` as follows.

### 7.1 Codec string from SPS (`describeCodec`)

SPS NAL layout (payload after the 1-byte NAL header whose low 5 bits are `7`):

```
NAL[0]     = 0x67 (usually; forbidden_zero_bit=0, nal_ref_idc=3, nal_unit_type=7)
NAL[1]     = AVCProfileIndication      (profile_idc)
NAL[2]     = profile_compatibility     (constraint_set0..5 + 2 reserved bits)
NAL[3]     = AVCLevelIndication       (level_idc)
NAL[4..]   = RBSP (with 0x000003 emulation-prevention bytes that must be removed when parsing)
```

`codecString = "avc1." + hex2(NAL[1]) + hex2(NAL[2]) + hex2(NAL[3])` (RFC 6381). Examples:
`42 00 1F` → `avc1.42001F` (Baseline level 3.1), `4D 40 1F` → `avc1.4D401F` (Main 3.1),
`64 00 1F` → `avc1.64001F` (High 3.1). `lib/scrcpy.js` `describeCodec(sps)` returns
`{ codecString, profileIdc, profile, levelIdc, level, constraintFlags }`, e.g.
`{codecString:'avc1.42001F', profile:'Baseline', level:3.1, ...}`.

Known `profile_idc` values: 66 Baseline, 77 Main, 88 Extended, 100 High, 110 High 10, 122 High 4:2:2,
244 High 4:4:4, plus newer ones (44, 83, 86, 118, 128, 138, 139, 134…). Level `level_idc = 31`
means level 3.1 (`idc / 10`); `level_idc == 11` with `constraint_set3_flag` means level 1b.

### 7.2 `avcC` (AVCDecoderConfigurationRecord) from SPS/PPS (`buildAvcC`)

`lib/scrcpy.js` builds the record mandated by ISO/IEC 14496-15 §5.3.3.1, which is what
`VideoDecoder.configure({ description: avcC })` expects for `avc1`:

| offset | size | value / field |
| --- | --- | --- |
| 0 | u8 | `configurationVersion = 1` |
| 1 | u8 | `AVCProfileIndication` = SPS[1] |
| 2 | u8 | `profile_compatibility` = SPS[2] |
| 3 | u8 | `AVCLevelIndication` = SPS[3] |
| 4 | u8 | `0b111111` + `lengthSizeMinusOne = 3` ⇒ `0xFF` (4-byte NAL lengths) |
| 5 | u8 | `0b111` + `numOfSequenceParameterSets = 1` ⇒ `0xE1` |
| 6 | u16 | SPS length |
| 8 | n | SPS NAL unit **without** start code |
| … | u8 | `numOfPictureParameterSets = 1` |
| … | u16 | PPS length |
| … | m | PPS NAL unit **without** start code |
| … | 4 bytes | only for High-family profiles (100/110/122/144/244/44/83/86/118/128/138/139/134/135): reserved+chroma_format_idc, reserved+bit_depth_luma_minus8, reserved+bit_depth_chroma_minus8, numOfSequenceParameterSetExt=0. The relay derives chroma/bit-depth from the SPS when it can parse it; for baseline/main it emits just the 11-byte header + SPS + PPS (the common form accepted by FFmpeg/Chrome). |

With `description = avcC`, an `EncodedVideoChunk`'s `data` must be in **AVCC** format: every NAL
unit of the access unit prefixed by `lengthSizeMinusOne+1 = 4` big-endian bytes of its length, and
**no** start codes. The relay also exports `annexbToAvcc(buffer)` to do exactly that conversion on a
scrcpy media packet. Alternatively, omit `description` and feed Annex-B chunks (Chrome's H.264
decoder detects start codes; SPS/PPS then have to be in-band), but the avcC + AVCC route is the
deterministic one and is what `lib/scrcpy.js` supports with metadata.

### 7.3 Decoder/session state rules

- Configure the decoder from a config packet or from cached SPS/PPS (`session.getVideoConfig()`);
  WebCodecs may require re-configure after resolution changes.
- Each **session packet** means: flush/reset the decoder; the next packet starts with a config
  packet then a key frame. `session.on('session')` / `onInit` reports the new width/height.
- Map touch coordinates in **video frame pixels** of the current session (see 5.2): for the plugin,
  scale the browser pointer position by `decodedFrameWidth / renderedWidth` and send
  `screenWidth = decodedFrameWidth`, `screenHeight = decodedFrameHeight`.
- PTS is in microseconds; use it for ordering/jitter tracking. The relay exposes arrival time
  (`recvTimeMs`) alongside each packet so the browser can measure queueing latency.

## 8. What `lib/scrcpy.js` implements

| protocol point | implementation |
| --- | --- |
| push + launch + version check | `ScrcpySession.start()` → `adb push`, `adb forward`, `adb shell CLASSPATH=... app_process ... 5.0.1 ...` with `audio=false tunnel_forward=true clipboard_autosync=false` |
| forward handshake with retry | connect+read-1-dummy-byte loop (deadline/attempts configurable), then second (control) connect, then 64-byte device name |
| reverse transport (optional) | `transport:'reverse'` → relay listens, `adb reverse`, accept video then control (no dummy byte) |
| video prelude + packet loop | codec id → session packet → bounded frame-packet parser; emits `onInit({codec,width,height})`, `onVideo({codec,isConfig,isKeyFrame,pts,data,recvTimeMs})`, `onConfig({avcC,codecString,sps,pps})`, `onSession({width,height})` |
| SPS/PPS → avcC + codec string | `splitAnnexBNals`, `buildAvcC`, `describeCodec`, `annexbToAvcc` |
| control messages | `sendTouch`, `sendKeycode`, `sendText`, `sendScroll`, `sendBackOrScreenOn`, `sendEmpty(type)`, `sendControlMessage(type, payload)`; device-message parser with `onDeviceMessage` |
| lifecycle | `stop()` closes sockets, kills the adb shell process, removes the adb tunnel, bounded buffers throughout |

Device capture test status: **blocked on hardware** — no adb-visible Android device is available on
this host (the AOSP ARM64 image cannot run on the SDK emulator without a hypervisor; an x86_64 AVD
also needs a hypervisor driver that cannot be installed in this environment; MuMu is out of scope).
No emulator was started or killed by this module. Instead, the protocol was verified against the
vendored v5.0.1 sources and by `spike/scrcpy/test-fake-device.js`: 160 assertions, including a full
end-to-end `ScrcpySession` run against a fake scrcpy-server that speaks the real TCP protocol
(handshake, codec id, session header, SPS/PPS config packet, 40 media packets, all control message
types delivered byte-for-byte, device→host messages, clean shutdown). That test writes
`spike/scrcpy/report.json` and `spike/scrcpy/capture-fake.h264`.

`spike/scrcpy/capture.js` is ready and unrun: as soon as any adb device is online, run
`node spike/scrcpy/capture.js --serial <serial>` (or without `--serial` to auto-detect). It captures
≥N packets to `spike/scrcpy/capture.h264`, verifies SPS/PPS/IDR + avcC, injects a tap through the
control socket, compares `adb` screenshots before/after, measures tap→first-frame latency, and writes
the real-device section of `report.json`. Therefore `capture.h264` is not present yet;
